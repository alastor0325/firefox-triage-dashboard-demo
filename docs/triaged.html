Steps to reproduce
1. Set `media.autoplay.blocking_policy != 0`. 2. Open https://mounirlamouri.github.io/sandbox/autoplay/webaudio.html.

It should not autoplay webaudio. Reporter follow-up: the gate at AutoplayPolicy.cpp:297-299 reduces to `StaticPrefs::media_autoplay_blocking_policy() != sPOLICY_STICKY_ACTIVATION` and therefore always returns true without checking permissions, with no AUTOPLAY_LOG traces to aid debugging.

Looking closer into this, it appears AutoplayPolicy.cpp:297-299 is really just `StaticPrefs::media_autoplay_blocking_policy() != sPOLICY_STICKY_ACTIVATION` according to AutoplayPolicy.cpp:158-161 and therefore always gives back true without even checking permissions etc.

AI reasoning

Reporter pinpointed the exact source lines: IsEnableBlockingWebAudioByUserGesturePolicy() (AutoplayPolicy.cpp:158) returns true only for sPOLICY_STICKY_ACTIVATION, and the AudioContext autoplay check at line 297-299 early-returns true when that helper is false — bypassing all permission/activation checks for the transient-activation and click-to-play policies. The HTMLMediaElement path (IsAllowedToPlayByBlockingModel at line 163) handles all three policies correctly, so the fix is to make the Web Audio path mirror that. S3/P3 because the bug only manifests when the user changes media.autoplay.blocking_policy away from its default of 0.

Findings investigated

Root cause: AutoplayPolicy::IsAllowedToPlay(AudioContext&) early-returns true whenever media.autoplay.blocking_policy != sPOLICY_STICKY_ACTIVATION, so Web Audio bypasses all permission/activation checks under the transient-activation and click-to-play policies.

Affected:
  • dom/media/autoplay/AutoplayPolicy.cpp:297-299

Related: bug 1511117, bug 2023365

Complexity: low

Only triggered when the user sets a non-default media.autoplay.blocking_policy. The HTMLMediaElement path uses a distinct helper (IsAllowedToPlayByBlockingModel) that handles all three policies — the Web Audio path is the outlier.

Thanks for the detailed analysis and the searchfox citations — you are right, this is a real gap. IsAllowedToPlay(AudioContext&amp;) at AutoplayPolicy.cpp:297-299 gates the rest of the Web Audio autoplay check on IsEnableBlockingWebAudioByUserGesturePolicy(), which only returns true for sPOLICY_STICKY_ACTIVATION (media.autoplay.blocking_policy == 0). For the transient-activation and click-to-play policies, the function short-circuits and Web Audio is allowed to play with no permission or activation check. The HTMLMediaElement path uses IsAllowedToPlayByBlockingModel, which has explicit branches for all three policy values — so the Web Audio path is the outlier and the gate needs to be reworked to mirror that. Adding AUTOPLAY_LOG traces in IsAllowedToPlay(AudioContext&amp;) is also worth doing here so this isn't as painful to diagnose next time.

Marking S3/P3 since the issue is only triggered when media.autoplay.blocking_policy is set away from its default of 0, but the fix scope is small and well-localized.
