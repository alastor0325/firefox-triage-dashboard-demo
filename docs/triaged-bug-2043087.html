Bug description (excerpt)

Run Frigate NVR and access the web UI from Firefox on Windows with default settings (media.wmf.media-engine.enabled = true). Navigate to the Recordings section and attempt to play back any recorded clip. Observe the video player error: NS_ERROR_DOM_MEDIA_NOT_SUPPORTED_ERR (0x806e0003) - Utility MF Media Engine CDM only support for media engine playback. Refresh the page and attempt playback again. Playback will succeed on some attempts and fail on others with no changes made between attempts. Non-DRM MSE video streams are intermittently and incorrectly routed to the WMF Media Engine CDM utility process, which rejects them with 0x806e0003 because it only supports DRM/EME media engine playback.

AI reasoning

MFMediaEngineDecoderModule::SupportInternal (dom/media/platforms/wmf/MFMediaEngineDecoderModule.cpp:97) reports HEVC HardwareDecode whenever media.wmf.media-engine.enabled is non-zero, without gating on EME / mMediaEngineId. PDMFactory::CreateContentPDMs (dom/media/platforms/PDMFactory.cpp:662) then registers the UtilityProcess_MFMediaEngineCDM RemoteDecoderModule for pref=2, and RemoteMediaManagerChild::CreateVideoDecoder (dom/media/ipc/RemoteMediaManagerChild.cpp:413) emits the observed 0x806e0003 because mMediaEngineId is empty for non-DRM playback. ExternalEngineStateMachine.cpp:342 already handles the analogous pref==2 + non-encrypted case at the state-machine layer but not the decoder-module layer. S3/P2: confirmed reproducible non-DRM HEVC MSE failure on Windows with a clear code-level routing fix; partial workaround (set pref to 0) exists, so not S2.

Findings investigated

Root cause: MFMediaEngineDecoderModule::Supports() reports HEVC as supported without requiring an mMediaEngineId, so for non-DRM MSE the PDMFactory selects the MFMediaEngineCDM utility path and CreateVideoDecoder later rejects with NS_ERROR_DOM_MEDIA_NOT_SUPPORTED_ERR (0x806e0003).

Thanks for the detailed report and the media profile — that's exactly what was needed.

Analysis

The profile (https://share.firefox.dev/4wS0c8h) shows that ExternalEngineStateMachine enters ReadingMetadata for your non-DRM HEVC MSE stream and then the decoder side fails with NS_ERROR_DOM_MEDIA_NOT_SUPPORTED_ERR (0x806e0003) - Utility MF Media Engine CDM only support for media engine playback. The root cause looks like a routing gap in MFMediaEngineDecoderModule::Supports(): it reports HEVC as supported on Windows whenever media.wmf.media-engine.enabled is non-zero (including the encrypted-only value 2) without checking whether the caller actually has a media-engine id / EME context. When PDMFactory then selects the UtilityProcess_MFMediaEngineCDM location for non-DRM HEVC, RemoteMediaManagerChild::CreateVideoDecoder rejects because mMediaEngineId is empty. The intermittency is consistent with PDM ordering: when the WMF/GPU HEVC path wins the Supports() race, playback succeeds; when the MFMediaEngineCDM module wins, it fails. The existing ExternalEngineStateMachine pref==2 + non-encrypted bailout fires on the state-machine path, but decoder-module selection is a separate path that needs the same gate.

Next Steps

This is enough information to investigate; I'll take a look. As a temporary workaround on your end, setting media.wmf.media-engine.enabled to 0 in about:config should keep MFMediaEngineCDM out of the picture entirely (you will still need to fully close and restart Firefox for the change to take effect). Please let us know if that workaround restores consistent playback.
