Thanks for the detailed report and the media profile.

Analysis

The profile (https://share.firefox.dev/4wS0c8h) shows ExternalEngineStateMachine entering ReadingMetadata for the non-DRM HEVC MSE stream, after which the decoder side fails with NS_ERROR_DOM_MEDIA_NOT_SUPPORTED_ERR (0x806e0003) - Utility MF Media Engine CDM only support for media engine playback. Root cause: a routing gap in MFMediaEngineDecoderModule::Supports() — it reports HEVC as supported whenever media.wmf.media-engine.enabled is non-zero (including the encrypted-only default 2) without checking for an EME / media-engine context, so PDMFactory can route non-DRM HEVC to the UtilityProcess_MFMediaEngineCDM, which rejects it because mMediaEngineId is empty. The intermittency is PDM ordering — whether the WMF/GPU HEVC path or the MFMediaEngineCDM module wins the Supports() race on a given load. The fix on our side is to gate the decoder-module Supports() check on the EME / media-engine context (or honor the pref's clear-vs-encrypted semantics).

There is likely a second, independent factor specific to a Frigate setup. Firefox caps concurrent hardware (DXVA) video decode sessions at 8 (media.wmf.dxva.max-videos), and HEVC on Windows has no software fallback (WMFVideoMFTManager returns a fatal error for HEVC/VP8/VP9/AV1 when HW accel is unavailable). So once that cap is reached, further HEVC streams fail outright — a different failure than 0x806e0003, and very easy to hit when many camera feeds play at once. Worth noting that the 8-stream cap is a Firefox-specific heuristic: Chromium has no equivalent fixed cap (per d3d11_video_decoder.cc and dxva_video_decode_accelerator_win.cc), and Microsoft documents no maximum decoder-instance count (ID3D11VideoDevice::CreateVideoDecoder, Supporting Direct3D 11 Video Decoding in Media Foundation) — both rely on the driver's own resource limits and fall back when decoder creation fails.

Why H.264 streams keep working but HEVC fails: H.264 has a built-in Windows software decoder (the Media Foundation H.264 MFT, Msmpeg2vdec.dll), so when the hardware path is unavailable — including when the 8-stream DXVA cap is hit — H.264 transparently falls back to software and keeps playing. HEVC has no software fallback in Firefox's Windows path: WMFVideoMFTManager returns a fatal error for HEVC/VP8/VP9/AV1 when HW acceleration isn't available, and WMFDecoderModule gates HEVC on DXVA being enabled. So under the same DXVA exhaustion, H.264 degrades gracefully to software while HEVC fails outright.

Next Steps — two things to try (please tell us which, if either, makes playback consistent):

A. Address the 0x806e0003 routing error: 1. Open about:config and set media.wmf.media-engine.enabled to 0. 2. Completely close and restart Firefox, then replay.

B. Test the concurrent-decoder cap (relevant because Frigate plays many streams at once): 1. Open about:config and raise media.wmf.dxva.max-videos from 8 to, say, 32. 2. Completely close and restart Firefox, then replay. (This is a temporary diagnostic — it trades more GPU memory for more simultaneous hardware decodes, not a permanent recommendation.)
