Bug description (excerpt)
Steps to reproduce
Use an Intel Mac (iMac20,1) running macOS. Ensure Firefox is set to automatically launch or restore a previous session containing media tabs upon user login. Keep media.hardwaremediakeys.enabled set to true (default). Log into the macOS user account, or launch Firefox immediately after a fresh login.
Actual
During initialization and session restoration at login, Firefox attempts to register hardware media keys before the system graphics architecture stabilizes. This causes a race condition within the SkyLight framework, triggering a segmentation fault (SIGSEGV) in Thread 0 at CGXRemoveHotKey / unregisterSpecialKey:forProcess:, completely crashing the host OS WindowServer. Workaround: Toggling media.hardwaremediakeys.enabled to false stops the crashes.

A quick observation on the crash itself for context:

The crashing process is WindowServer, not Firefox — the entire crashing stack is inside Apple's SkyLight framework (CGXRemoveHotKey → -[CPXSpecialKeyEventProcessor unregisterSpecialKey:forProcess:] → cleanupForProcessDeath: → WhackProcess). That's WindowServer's per-process hot-key cleanup path firing when a client process exits, and it null-derefs inside WindowServer's own internal hot-key list. There is no Firefox frame on the crashing stack.

Also worth noting: Firefox's hardware media-key support uses CGEventTapCreate(kCGSessionEventTap, ..., CGEventMaskBit(NX_SYSDEFINED), ...) to listen for system-defined media key events (widget/cocoa/MediaHardwareKeysEventSourceMac.mm). It does not call the CGXRegisterHotKey / CGSSetSymbolicHotKey SPI that the crashing CPXSpecialKeyEventProcessor path manages — those are different macOS keyboard APIs. So while toggling media.hardwaremediakeys.enabled may change the timing of when Firefox starts/stops its event tap (and thereby change whether the WindowServer race fires), the immediate null deref is in WindowServer's own state, not in anything Firefox controls.

This looks like an Apple OS bug; please do file it via Feedback Assistant as Steve suggested, and share the FB# here for tracking. The Widget: Cocoa folks can decide from there whether there's a Firefox-side workaround worth pursuing.
