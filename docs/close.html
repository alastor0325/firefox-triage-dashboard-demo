Duplicate of bug 1711812 (10-bit/High 10 / yuv420p10 H.264 fails on Windows; bwerth@mozilla.com). MAINTAINER QUESTION ANSWERED (gecko-navigator, rev 302a821d49e9): the 10-bit limit is NOT an artificial cap and is NOT pref-controllable. WHERE: the only explicit H.264 color-depth gate is D3D11DXVA2Manager::SupportsConfig, MFVideoFormat_H264 branch -> NS_ENSURE_TRUE(mColorDepth==ColorDepth::COLOR_8) at DXVA2Manager.cpp#479 (VP9/AV1 allow COLOR_10 in the same function; H.264 does not, because there is no DXVA2 decode GUID for High 10 H.264 -- the H.264 GUIDs are 8-bit 4:2:0 only). WMFDecoderModule::SupportsColorDepth returns true unconditionally (defers to DXVA). PREF: none. No 10bit/color-depth key in StaticPrefList.yaml. media.wmf.force.allow-p010-format governs HDR P010 output-surface selection, not this gate. REMOVING THE GATE WON'T HELP: all three Windows H.264 paths are 8-bit-only by construction -- DXVA (no High 10 GUID), WMF software MFT (8-bit 4:2:0 only), and ffvpx (H.264 decoder compiled OUT: CONFIG_H264_DECODER 0 in media/ffvpx/config_components_audio_video.h#130; FFmpegDecoderModule routes H.264 only for Linux-system-ffmpeg & Android). Removing line 479 just defers the failure. EDGE: Chromium bundles a full software H.264 decoder with High 10 support (Firefox deliberately strips H.264 from ffvpx for licensing) [speculation on exact Edge internals]. REAL FIX SCOPE: bundle/enable a software High 10 H.264 decoder (e.g. ffvpx CONFIG_H264_DECODER) -> a licensing/policy decision, not a code/pref flip. Resolution stays DUPLICATE of 1711812; this bug adds no new diagnostic info. P/S untouched.

MSDN VERIFICATION (per alwu request): the official Microsoft 'H.264 Video Decoder' MFT doc (https://learn.microsoft.com/en-us/windows/win32/medfound/h-264-video-decoder) confirms the 8-bit-only claim: Output Types are only I420/IYUV/NV12/YUY2/YV12 (no P010/P016 10-bit format); Format Constraints state '4:2:0 chroma or monochrome'; and supported profiles are Baseline, Main, and High up to level 5.1 -- High 10 is NOT listed. So the WMF software H.264 MFT cannot emit 10-bit output, confirming that removing the DXVA2Manager.cpp#479 COLOR_8 gate would not enable 10-bit H.264 playback. Finding stands.

Thanks for the report, Jake. This is the same issue as bug 1711812 (yuv420p10 (10-bit) H.264 fails to play), which is already being investigated by :bwerth.

The underlying limitation is that the platform H.264 decoders on Windows (Media Foundation) and macOS (VideoToolbox) do not support the 10-bit (High 10 / yuv420p10) profile — they only support 8-bit. On Windows specifically, our DXVA path explicitly requires ColorDepth::COLOR_8 for H.264, and the WMF software H.264 MFT also doesn't produce a usable 10-bit output. Edge can play this because Microsoft Edge has additional codec support beyond what's exposed through the public Media Foundation H.264 MFT. macOS appears to work for you, but on other reporters' macOS systems the bottom of the frame glitches (bug 1743824) — VideoToolbox technically accepts the stream but doesn't decode it cleanly.

Closing this as a duplicate of bug 1711812 so all the discussion stays in one place. Please follow that bug for updates.
